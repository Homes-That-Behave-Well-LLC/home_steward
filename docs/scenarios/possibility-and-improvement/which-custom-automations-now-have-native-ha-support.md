# Which custom automations now have native HA support

Status: CANONICAL SCENARIO

Developed-content maturity only; not Owner, runtime or architecture acceptance.

> Proposed synthetic scenario; no inspected/replaced real household automation.
> Applies [discovery](../../architecture/possibility-and-improvement-discovery.md) and [architecture stewardship](../../architecture/htbw-architecture-stewardship.md).

## 1. Household request

"Are we maintaining custom logic that Home Assistant now supports natively?" Identify exact accepted
behavior and version, not merely a native feature with a similar name.

## 2. Existing HTBW knowledge

Foundation configuration/participation; governed household outcome/acceptance references; Truth
Historical Facts; native Decision Traces; Stewardship existing maintenance obligations.

## 3. Authorized private retrieval

Minimum approved automation/script behavior, original requirements, configuration/change and tests/
acceptance references. No credentials or broad private code/log access implied.

## 4. Optional public research

[2026.11 target exclusions](https://www.home-assistant.io/blog/2026/11/04/release-202611/) and
[official target semantics](https://www.home-assistant.io/docs/automation/targets/) can ground a
conditional native-path inquiry. No claim an actual household script matches.

## 5. Home Steward synthesis

"This custom implementation may now have a simpler native path." Require behavior-equivalence
analysis: targets, exclusions, groups/dynamic membership, timing, manual control, exceptions,
authority, source/observed outcome, failure/degradation and retained household benefit.

Compare accepted outcome with current custom behavior and verified native capabilities. Define
acceptance tests and migration/rollback before any replacement; measure maintenance/Technical Debt
impact and new dependency/support obligations. Native existence alone never justifies replacement,
especially if intentionally beneficial fallback or governed scope would be lost.

## 6. Provenance

Exact implementation/outcome/version references, official publication/review/effective and installed
version, GA/Labs/preview/deprecation/removal state; gaps and inferred equivalence are not Truth.

## 7. Candidate relationships

Custom-to-native equivalence is a review candidate, not accepted replacement or a model diagnosis.
Unresolved official behavior blocks migration advice.

## 8. Household confirmation

Confirm intended behavior/current value through an eligible participant; this is evidence, not
permission to disable or replace the custom logic.

## 9. Governed durable relationship

Responsible configuration/capability owners govern accepted migration records; original rationale,
history and Trace remain intact. No new migration schema or authoritative write.

## 10. Proposed actions

Offer governed requirements/equivalence review via HTBW/Operational Trust, with obligations,
rollback/removal, tests, HA-DEV/lived validation and Owner acceptance before retirement.

## 11. Prohibited autonomous actions

No replacement/removal or automation/script generation/enablement, configuration/policy/preference/
obligation edits, HA update/rollback, Labs/integration/entity enablement or upstream contribution.

## 12. HTBW authority

Foundation mechanism/configuration; Truth Facts; Stewardship care; Identity requester; Continuity
intent; Operational Trust authorization; Concierge formulation/orchestration/Trace.

## 13. Privacy and locality

Minimal authorized code/configuration/source scope; no secret/log uploads. Local derived comparisons
inherit privacy/audience/lifecycle; original owners retain authoritative state.

## 14. Unavailable / degraded behavior

Unknown accepted behavior, stale official docs or missing test evidence yields "I don't know whether
replacement is equivalent". Keep native/custom operation unchanged.

## 15. Acceptance expectations

Equivalence, acceptance, migration/rollback and Technical Debt impact explicit. Native existence is
insufficient; no custom behavior is removed before separately governed validation/acceptance.

## 16. Open questions

Exact behavior/test coverage, migration owner and acceptance mapping remain future work; no code
generation, replacement, test execution, watcher or ingestion.
