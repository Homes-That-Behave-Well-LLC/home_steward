# Prepare an HTBW native-capability migration review

> Proposed synthetic review package; no migration, deployment, retirement or Owner acceptance.
> Applies [HTBW Architecture Stewardship](../architecture/htbw-architecture-stewardship.md).

## 1. Household request

"Prepare the governed review for moving this HTBW behavior to a Home Assistant-native capability."
Resolve exact accepted outcome/versions and authorized reviewer, not a command to execute migration.

## 2. Existing HTBW knowledge

Accepted outcome/rationale/contracts, current behavior/configuration/data/adoption, implementation/
test/acceptance and dependency references; Foundation model, Truth Facts and Decision Traces.

## 3. Authorized private retrieval

Minimum approved exact decisions/issues/contracts/specifications/implementation/test and recovery/
acceptance evidence. Each private repository/Owner record/log source is separately governed.

## 4. Optional public research

Current official release/developer/integration sources, beginning with [HA developer documentation](https://contributors.home-assistant.io/core/),
verify native behavior. Incomplete official proof blocks migration advice; no private package uploads.

## 5. Home Steward synthesis

Prepare the review package, including every required element:

1. Current accepted household outcome.
2. Existing HTBW behavior.
3. Original rationale/platform limitation.
4. Native HA candidate.
5. Authoritative sources and installed/effective versions.
6. Behavioral-equivalence analysis.
7. Responsibility-boundary analysis.
8. Privacy and authority analysis.
9. Data/configuration migration.
10. Failure/degradation comparison.
11. Performance comparison.
12. Diagnostics and Explainability/Decision Trace.
13. Affected issues/ADRs/contracts/specifications.
14. Separately authorized implementation plan/dependencies/owner.
15. Rollback/recovery plan and reversibility limits.
16. Unit/static/type checks and applicable integration tests.
17. HA-DEV exact-version validation.
18. Reference Home lived validation.
19. Owner acceptance requirement.
20. Retirement criteria for superseded HTBW logic.

Expected benefit/Technical Debt reduction and new maintenance/privacy/vendor/support obligation must
be explicit. Comparison covers ordinary paths, exceptions, manual control, identity and history.
Superseded logic is not retired before exact replacement validation and attributable Owner acceptance.
This package is consultation/draft, not a completed test, approved implementation or migration.

## 6. Provenance

Source location/version/commit and publication/commit date, review date, installed/effective HA
applicability, GA/Labs/preview/deprecated/removal state and evidence gaps. Inference is not Truth/acceptance.

## 7. Candidate relationships

Proposed native equivalence/replacement remains a candidate, not an obsolete/reopened decision or
accepted migration. Future reconsideration fields are not retrofitted to current ADRs/Ledger.

## 8. Household confirmation

Eligible human confirms outcome/scope for review only. Package receipt or conversational agreement
does not authorize implementation, satisfy acceptance or permit retirement.

## 9. Governed durable relationship

Existing decision/configuration/acceptance/history owners govern any later approved records.
Home Steward cannot write Ledger/ADR/acceptance, close issues or create a centralized approval store.

## 10. Proposed actions

Return the draft through HTBW/Operational Trust and the responsible human implementation/governance
process. Rollback, tests, HA-DEV and Reference Home lived evidence precede Owner acceptance/retirement.

## 11. Prohibited autonomous actions

No migration/deployment/retirement, code removal, decision reopening, Ledger/ADR edit, issue create/
close, automation/configuration/policy changes, HA update/Labs enablement or upstream contribution.

## 12. HTBW authority

Foundation data/configuration; Truth Facts; Identity reviewer; Stewardship care; Continuity context;
Operational Trust authorization; Concierge formulation/orchestration/Trace, not acceptance owner.

## 13. Privacy and locality

Minimum approved source/Person/purpose/audience package; local derivations inherit lifecycle.
Recovery cannot resurrect revoked source grants; private credentials/reviews are never public inputs.

## 14. Unavailable / degraded behavior

Missing official equivalence, historical rationale, recovery or acceptance evidence is explicit:
"I don't know whether this can migrate safely." Preserve native/custom behavior; no fabricated sign-off.

## 15. Acceptance expectations

All twenty package elements, unchanged governance/Trace, equivalence/privacy proof and rollback.
Unit tests are not lived validation; no code retirement before HA-DEV, Reference Home and Owner acceptance.

## 16. Open questions

Future exact package/source/approval mapping and separately authorized validation remain open;
no ingestion, code generation, migration executor, HA-DEV action or runtime implementation.
